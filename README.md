# DingBell

Open-source AI customer support for ecommerce teams, built on Flue and Cloudflare.

Its `prepare_reply` tool saves the original body/citations and schedules a bounded, persistent controller alarm; the sender accepts only the original completed, fully settled Flue execution with current input, policy, knowledge, budget, credentials and channel authority. AI queue records use schema 2 and null staff actors; schema 1 human replies retain their existing contracts. Both share store-wide rate limits and one provider attempt per intent. ## Development

Use Node.js 24.14.0 and install the locked dependencies:

```sh
npm ci
npm run check
npm run test:flue
npm run dev
```

Open `/login` on the local URL printed by Vite. Without identity configuration it shows an explicit unavailable state; no model or Ozon keys are needed. `/workspace` requires a verified account and lists only its companies. `/api/health` reports application liveness, not cloud resource or provider readiness.

Local checks do not need Cloudflare login or model credentials. Module tests run at most four files concurrently to bound local Miniflare/loopback resource use; concurrency scenarios inside each test remain unchanged. The integration test uses Pi's official faux provider, synthetic messages and a temporary local Durable Object store. It starts and stops its own development server and removes that temporary store after the test.

For local identity development, copy `.dev.vars.example` to `.dev.vars`, set a unique random `BETTER_AUTH_SECRET` of at least 32 characters (for example, generate one with `openssl rand -base64 32`), and set `APP_BASE_URL` to the exact origin used in the browser. Run `npm run db:migrate:local` before starting the application. Production origins require HTTPS; HTTP is allowed only for explicit loopback hosts. These files and secrets must stay untracked.

`GET /api/setup` reports whether identity and mail configuration are present. It does not test database availability, migrations or email deliverability. Public self-service registration and arbitrary company creation remain closed. There is no production seed endpoint or default account.

To create the first company, configure `RESEND_API_KEY`, a verified sender mailbox in `MAIL_FROM`, and a separate random `BOOTSTRAP_SECRET` of at least 32 characters. Open `/setup` and enter the installation secret in the form, never in the URL. Claim the installation with the company name and owner's name/email, set a password, and verify that email. Return to the same installation, authenticate with the verified owner's password, then select the created company. Refreshing the page requires re-entering the installation secret; progress is retained in D1. An interrupted claim does not expire into a fresh installation or promote an existing account. Once initialization finishes, the endpoint permanently closes and the deployment secret can be removed.

Owners and administrators can open `/workspace/team` to invite members or administrators, resend pending invitations, and revoke them. The recipient registers or signs in using the invited email, verifies it, and explicitly accepts the invitation. An old invitation cannot restore a removed membership. `/forgot-password` and `/resend-verification` acknowledge requests without revealing whether an email exists; `waitUntil` attempts delivery but is not a durable retry queue. Provider acceptance does not prove inbox delivery. Password reset invalidates earlier sessions.

The team page also supports role changes and member removal. Administrators can manage members and other administrators; only owners can grant or change ownership. Any change involving an owner requires the acting owner's current password. To hand over ownership, first grant another member the owner role, then change your own role; these are separate confirmed operations. A company must retain an owner. Removing a member does not delete the account, historical audits or memberships in other companies. New requests recheck membership, and the UI discards its old identity and company caches after a member change or an uncertain result.

Migrations contain application constraints beyond the generated Better Auth schema: unique company/user memberships, unique pending company/email invitations, three invitation-completion triggers in `0003_invitations.sql`, and two last-owner guards in `0004_membership_guards.sql`. Preserve these when regenerating the auth schema. Completed invitation flow records must survive member removal. Existing duplicate data makes migration fail rather than being silently deleted; inspect and reconcile it before deployment. The last-owner guards also reject deleting an owning user; account/company deletion is not exposed by the application.

Authentication and password confirmation use Better Auth. Member role updates and removals use a narrow conditional D1 write because the pinned SDK's member writes only filter by member ID. The final write also checks the company, displayed role, current actor membership, verified account and unexpired session. A stale target returns a conflict; owner guards run atomically in D1. Audits record the actor, company, target member and intended role change, without passwords. If the result audit fails after a write, the response is uncertain and clients must reread instead of replaying it.

Owners and administrators can manage Ozon connections at `/workspace/stores`. Saving a store only encrypts and stores its credentials. A separate read-only check samples credential access, product lists, chat lists and FBS order lists; each result is independent and expires after 24 hours. Replies and proactive chat creation remain unverified. These capability checks do not synchronize customer data or enable customer messaging. Pause preserves credentials; resume requires a new check; disconnect removes stored credentials while retaining the store and audit history. To reconnect a disconnected store, replace its credentials and check again.

Before saving credentials, set `STORE_CREDENTIAL_KEYS` in the ignored `.dev.vars` file to a JSON object such as `{"v1":"<base64-encoded 32 random bytes>"}` and set `STORE_CREDENTIAL_ACTIVE_KEY=v1`. Generate the key independently with `openssl rand -base64 32`; do not reuse the identity secret or a platform API key. On Cloudflare, store the key map as a Worker secret. Encryption uses native AES-256-GCM with a fresh nonce and company/store/account/revision context. Missing encryption configuration leaves account and existing metadata access usable while blocking credential writes and checks. API keys are never returned to the browser.

Owners and administrators have access to all stores in their company. Ordinary members only see explicitly granted stores; newly created stores grant them no access automatically. Grants reference the current membership, so removing a member deletes those grants and accepting a later invitation does not restore them. Migration `0005_stores.sql` enforces same-company store/member relationships. The credential envelope, current capability evidence and revision share one store row so conditional writes cannot leave a partially updated credential set. Audit events are separate and survive membership removal.

Platform credential replacement increments its version and invalidates old capability results. Encryption key versions are separate: retain old entries in `STORE_CREDENTIAL_KEYS` to decrypt existing records while new credential writes use the active key. This release has no bulk re-encryption command; do not remove an old key until every dependent record and retained backup has a tested recovery path. Back up encryption keys separately from D1. An uncertain write response must be checked by rereading the store, never by automatically resending the mutation.

After a fresh credential and chat-list check, a manager can separately enable buyer-chat synchronization. Each store has a `StoreCoordinator` Durable Object; alarms process one bounded provider page, while a minute Cron scans at most 50 due stores to repair missed wakeups. D1 separates each source’s enabled intent from the shared store lease, preserving checkpoints, messages and ingestion events. A page and its cursor commit atomically. Stopping, pausing, disconnecting or replacing credentials prevents old results from committing and preserves already imported history; resuming synchronization requires an explicit manager action. The continuing authorization belongs to the company and does not expire when the enabling manager signs out.

Only `BUYER_SELLER` chats are imported. Initial history and incremental reads have separate checkpoints; provider IDs retain exact precision, repeated messages are deduplicated, and conflicting original content stops the page rather than overwriting it. Forward-read evidence can mark a message first seen during history import as newly observed, while excluding the requested boundary message. An initially empty chat uses a Backward read without an invented message ID to establish its first historical baseline; any remaining backfill is reopened in the same transaction. There is no AI consumer or customer send path yet. Attachments are not fetched and message content is treated as untrusted data. Store details show imported counts, progress and errors; the message center reads those persisted originals.

Synchronization respects persisted `Retry-After` deadlines across stop/start and credential replacement, retries transient failures at most five times, and retains the latest eight page boundaries to detect recent cursor cycles. This is not proof against arbitrary-length pagination cycles. Only synchronization calls currently share the DO request budget; capability checks remain separate. Actual Ozon history pagination, entitlement behavior and inclusive/exclusive boundaries still need authorized platform verification; synthetic tests are not a substitute. Migration `0006_message_sync.sql` adds immutable-message protection; `0007_source_sync.sql` preserves existing chat data while separating shared coordination from source authorization. Migration `0008_fbs_postings.sql` adds the FBS source while preserving existing data and invalidating old leases. Lifecycle and immutable source-observation triggers must be preserved when regenerating schema.

Read-only product and FBS posting adapters share the bounded transport; both now participate in scheduled synchronization. They share the chat adapter's fixed-host, runtime allowlist, eight-second deadline and 1 MiB response limit. Product reads retain exact IDs, source SKU relationships and decimal-string prices; missing details do not imply deletion or publish knowledge. FBS reads use `/v4/posting/fbs/list` and `/v3/posting/fbs/get`, with an application limit of 100 postings per page and 31 days per request. Split postings retain their own identity and raw status. Business dates are not treated as source versions. These adapters currently have synthetic Node/workerd coverage; real product pagination and FBS status semantics remain unverified. FBO/rFBS coverage, complete provider verification and reliable status-transition semantics remain pending.

Product synchronization has its own capability requirement, enable control, epoch and progress. The shared coordinator fairly selects due chat/product/FBS work and enforces one store-wide lease and request interval. Product lists durably queue detail reads before advancing their cursor; list pages and detail batches alternate. Empty list pages end an observed round, followed by a five-minute rescan. Missing details retry three times without deleting old facts. Stop/resume preserves the cursor and retries outstanding failures explicitly. Source snapshots record observed facts and changes; they do not publish knowledge or enable AI replies. Existing facts, pending refreshes and failed reads can overlap, which the interface explains. A source-specific permission denial stops only that source; invalid credentials, store pause and credential replacement stop all sources.

FBS synchronization has a separate `orders_fbs_read` capability and control. It starts with an explicit 30-day history budget, then follows frozen query windows with a one-hour overlap and at most 31 days per request window. Only the final provider page advances the completed window boundary. Long downtime is caught up in segments instead of jumping to the newest month. Existing postings retain independent list/detail observations and exact split-posting identities. Successful details become due again after 15 minutes, including postings no longer present in new list windows; this is a scheduling interval, not a refresh SLA under backlog or limits. A failing detail retries three times without deleting prior facts or blocking other postings. Raw statuses are observations, not reliable ordered transitions, and never trigger notifications in this release.

The frontend uses official ShadCN Nova/Base UI components, locally bundled Geist/Noto Sans SC fonts, TanStack Query, React Hook Form and Valibot response validation. Authentication changes discard the old query client and mounted company state. Offline or unverified workspace state is hidden until the server can revalidate it. Uncertain mutations are checked with reads rather than automatically resubmitted. Customer support modules are visibly unavailable until implemented; no demo messages or statistics are presented as live data.

### Durable inbound delivery

The existing minute-based scheduled Worker now consumes committed live customer events through bounded delivery leases. The conversation controller records each accepted event once, restores the needs-reply state, and reopens resolved conversations while preserving human ownership. An AI-owned conversation stores its next input durably and revokes the old run before new admission. Lost acknowledgements replay the original receipt; takeover removes the pending target. A prior admitted execution must have verified financial closure before replacement. A separate bounded classification run submits stage/language metadata through a durable tool; the server selects a frozen policy and a distinct answer target. Classification and answer runs share the financial ledger but reserve separately, and classification must close before the answer can start. Unknown classifications hand off; restarts and retries retain the original decision. A durable dispatch directory now connects these steps to the scheduled Worker: source acknowledgement and dispatch are atomic, newer input replaces the target, and expired workers cannot finish newer work. Disabled reception, denied admission and bounded timeouts return eligible conversations to humans; delayed classifier observations cannot stop an answer already in progress or a later human-resumed run. Migrations 0037–0040 preserve prior audit, source and financial records without backfilling processed input. That dispatch milestone exposed only handoff; the opt-in knowledge tool is described above. Order tools, final AI sending, real-model quality, production latency and multi-tenant capacity remain unaccepted. See architecture sections 7.24–7.26 and implementation progress sections 80–82.
