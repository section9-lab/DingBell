# Identity compatibility probe

This isolated Worker validates Better Auth 1.7.7, the official Drizzle adapter 1.7.7,
Drizzle ORM 0.45.4, and D1. It contains no product UI, Flue Agent, real mail sender,
shop integration, model call, or production installation flow. The formal DingBell
Worker does not import this directory.

All routes except `GET /api/health` require the server's `PROBE_TOKEN` bearer secret.
Missing probe/auth configuration fails closed. Captured verification links are stored
only in the isolated D1 database, require bearer authorization to read, and are never
written to application logs. Use synthetic `example.invalid` accounts with this runner.
Health reports process availability, not database readiness.

## Schema and local checks

The authentication and organization schema is generated by the official Better Auth
CLI, including the organization plugin. Only the `probe_*` tables are handwritten.
Run from the repository root using the installed, locked versions:

```sh
node node_modules/auth/dist/index.mjs generate --config probes/identity/schema-config.ts --adapter drizzle --dialect sqlite --output probes/identity/src/auth-schema.ts --yes
node node_modules/drizzle-kit/bin.cjs generate --config probes/identity/drizzle.config.ts
node node_modules/typescript/bin/tsc -p probes/identity/tsconfig.json --noEmit
node --test tests/integration/identity.test.ts
node node_modules/vite/bin/vite.js build --config probes/identity/vite.config.ts
```

The integration test applies Wrangler migrations to a fresh temporary D1 database,
applies them again, and runs the shared HTTP contract against actual workerd. After
writing accounts, sessions, memberships, and a tenant document, it stops the Worker,
reapplies migrations, and restarts with the same database and auth secret. It then
checks that the original cookie and data still work. Temporary state and subprocess
groups are removed after the test, including failure paths.

Contracts include registration, email verification, login, invalid password, session
retrieval, server-side logout invalidation, invitation email matching, mandatory
verified email for invitations, revocation, concurrent/repeated acceptance, company
read/write isolation, and immediate membership removal enforcement with an old session.
Separate runtime checks verify missing probe or auth secrets return 503.

## Probe policy and limits

Unverified accounts may log in **only to make the organization plugin's verified-email
guard observable**. `requireEmailVerificationOnInvitation: true` is explicit. This
probe policy is not the production registration policy. Sending mail means capturing
it in D1; the probe never claims successful external email delivery.

The official Drizzle adapter uses `transaction: false`: D1 does not support interactive
transactions. Passing these contracts does not prove atomic user/organization/bootstrap
creation. The bootstrap mode below separately tests recoverable installation checkpoints.
The tenant document route demonstrates explicit session and membership
checks, not automatic RLS or the complete product authorization matrix.

## Isolated cloud use

`wrangler.jsonc` intentionally contains an invalid-for-cloud local database ID. Before
building a cloud probe, the operator must supply the unique test database ID through
`DINGBELL_IDENTITY_DB_ID`; the Vite config injects it into the generated Wrangler config.
No account or cloud resource ID belongs in this repository.

Apply the committed migrations with Wrangler using that generated configuration and
the isolated database. Provision `PROBE_TOKEN` and `BETTER_AUTH_SECRET` as Worker secrets,
and `BASE_URL` as the probe's HTTPS origin, before running:

```sh
node probes/identity/run-check.ts
```

The runner reads `DINGBELL_IDENTITY_BASE_URL` and `DINGBELL_IDENTITY_TOKEN` from its
environment. Its output contains contract names and a synthetic run ID, not cookies,
passwords or mail links. It creates fresh synthetic users and organizations on each run.
The shared cloud runner does not claim to restart the deployed Worker or apply migrations;
the operator must separately verify those steps. Do not point it at a product database.

## Bootstrap mode

The installation fixture follows architecture section 4.3: a unique D1 row is claimed
atomically, then moves from `provisioning` to `initialized`. Only the same claim may
continue after its execution lease expires. Expiry never deletes ownership or reopens
public claim. There is no reset endpoint. Passwords and installation secrets are not
stored in the job. Only Better Auth public APIs create identities and organizations.

Before creating a user, the task stores a random expected user ID. A scoped instance
of Better Auth uses its public `advanced.database.generateId` option for that user.
On recovery, an actual sign-in must return that ID; a pre-existing email belonging
to another identity is rejected without changing its name, password or ownership.
The organization uses a stable opaque slug and is checked through the public
organization API, so recovery reuses its completed creation.

Every bootstrap route also requires `x-bootstrap-authorization: Bearer <BOOTSTRAP_SECRET>`.
`GET /__probe/bootstrap/status` exposes state and checkpoint flags, not the owner's
email or name. Claim and resume return 410 after completion. Missing installation
configuration returns 503; missing or wrong credentials return 401.

To run failure injection against an isolated deployment, explicitly set Worker var
`BOOTSTRAP_TEST_HOOKS=true`, provision `BOOTSTRAP_SECRET` as another random Worker
secret, and supply the same secret to the runner through
`DINGBELL_IDENTITY_BOOTSTRAP_SECRET`:

```sh
node probes/identity/run-check.ts bootstrap
```

This is a **once-per-database** scenario. It injects a 503 immediately after a successful
user API and again after a successful organization API, before saving their checkpoints.
A guarded test clock expires only the execution lease. The local integration test also
stops and restarts actual workerd at both interruptions. The shared cloud runner, unless
its optional interruption callback is provided by an operator harness, verifies only
the injected request interruptions and durable checkpoint protocol, not a cloud reset.

The separate `bootstrap-occupied` mode requires a different fresh test database and
verifies that an existing email account is not appropriated. It deliberately leaves
that initialization task incomplete; it never resets or reopens it. The default
`run-check.ts` mode remains the repeatable identity suite.

These are probe contracts, not a product installer. Interruptions inside Better Auth's
own multi-write API implementation, production signup policy, installation UI and
operator recovery tooling require separate implementation and acceptance.
