# DingBell 开源 AI 客服系统施工方案

版本：0.2，评审稿。编制日期：2026-10-08。

**2026-10-11 开发保存点：** 已完成 6B-20，本轮已收尾，后续实施暂停。剩余 **26 个必做工作包、3 个可选商业工作包**及下次恢复顺序保存在[实施计划第 11 节](01-implementation-plan.md#11-开发保存点与后续计划2026-10-11)。

当前推进到 6B-20：独立 `support-reply-v1` 受控工具保存不可变回复，持久化闹钟及时核对原生 Flue 的成功完成和全部生成用量结清，再接入现有共享限流及单次尝试发送器。AI 使用空员工身份的独立回执，人工回复原契约不变；接管、输入/策略/知识/渠道变化或原期限失效阻止未发起的请求，历史回执不重新排队，不明确结果不自动重发。消息中心兼容受控 AI 发送编号。部署三开关和店铺外发权限仍默认关闭；本地合成验证不代表真实模型质量、Ozon 外发或云端验收。私有订单归属、嵌入实际费用、跨账本核对及云端/一键部署仍待推进。详见架构 7.12–7.31、实施进度第 68–87 节。

6A-6 接入有版本的 NVIDIA JSON schema 约束，保留旧运行参数，复用现有 Valibot 转换器。9 个失败样本三轮共 27 次真实复测未再出现字段结构错误，仍有 7 次决策不符及人工等待措辞风险，尚不开放自动回复。见架构 7.11、实施进度第 67 节。

本方案用于决定 DingBell 怎样实现、怎样验证、怎样交付。用户已同意逐步实施，当前已完成阶段 2 身份/公司/店铺基础的本地验证，并推进到阶段 5B-11 中俄语义初测（固定 12 份合成资料、36 个问题，取得真实 BGE-M3 嵌入并验证离线重放；知识缺口、人工修订与独立发布已接通。分数分布证实不能将统一相似度阈值当作可回答判定，生产质量和 AI 调用接线仍待验收）；阶段 1、3、4 仍有真实平台、云端或 AI 接待相关验收未完成。文中的接口、表结构、配置名和测试编号仍是施工合同，实际完成范围以[实施进度](06-implementation-progress.md)为准。

6A-1–6A-3 已接通受控问答测试：服务端冻结原消息/策略/知识，独立管理嵌入准入与生成预算，经 Flue 原生执行和引用复核返回模拟结果。所有者/管理员可在消息中心打开 ShadCN 测试面板，先检索依据，再生成测试回复；刷新恢复原编号，未知操作不自动重试，旧上下文失效时隐藏结果。本地 D1/DO、Flue 与浏览器验证使用合成模型响应，不会外发客户消息。6A-4 新增公司设置中的测试预算管理：默认暂停、固定窗口/上限、启停与审计原子保存、未知提交主动核对；展示公司生成余额和独立的检索额度。真实回答质量、后台结算修复、自动接待和最终发送仍待验收；见实施进度第 62–65 节、架构 7.7–7.9。6A-5 已建立 200 例合成问答评估和真实 NVIDIA 采样，发现引用格式、决策与虚假转接措辞问题；候选 v2 提示词按持久版本选择，仍未通过自主回复质量门槛。结果和边界见实施进度第 66 节、架构 7.10。

已确认的方向是：优先 Ozon；首版完整部署到 Cloudflare；Vercel 后续适配；开源自部署与商业 SaaS 共用核心代码；公司是协作与数据隔离边界；界面沿用当前 shadcn/ui 风格的 Figma 设计。

当前消息中心支持公司/店铺权限过滤、精确标识查找、会话与原文分页、ShadCN 消息布局及窄屏详情抽屉；4B1 增加持久认领、接管、解决和异常后的状态核对，4B2 补齐人工重新打开，4B3 增加详情中的等待消费者、等待内部和返回待回复，4B4 补齐负责人分配/转交、候选权限与原因审计，4B4a 增加负责人姓名、失权和成员移除展示，4B5 补团队内部备注、作者快照、有界分页与原命令重试，4B6 增加全部/我负责/未分配队列、工作状态筛选和同快照计数。4C1 增加人工纯文本发送后端、单次平台尝试、共享限流与未知结果恢复，真实外发默认关闭。已接通原文回复编辑器、确认发送、最近结果及未确认提交恢复。新消息触发的状态变化与剩余阶段验收仍待完成；增量读取和同标签页恢复见下述 4D3，不代表阶段 4 整项验收通过。

4C3A 补充翻译调用前的预算与运行存储：默认关闭、原子预留、原成员绑定、配置快照及幂等用量结算。尚未接入翻译接口或模型执行；原文人工回复继续沿用现有流程。具体测试范围见实施进度第 36 节。

4C3B1 在此基础上接入内部 Flue 翻译 Agent 与持久调用许可，验证重启、实例丢失和框架重试不能产生第二次供应商 HTTP。沿用官方 NVIDIA Provider，检查原始响应中的用量字段，原生 HTTP 入口仍关闭。面向用户的翻译接口、结果核对和俄语预览尚待接线；不会因此开启自动客服或真实店铺发送。具体边界见实施进度第 37 节。

4C3B2 接通有原成员绑定的翻译提交/读取接口。服务端选择配置和预算，原 POST 可恢复原回执，GET 不派发模型；等待后的正文再次验权，迟到费用仍记原预算。界面翻译确认、服务端发送来源关联、预算管理和无人读取时的自动核对尚待后续步骤，翻译与真实外发仍分别默认关闭。具体证据见实施进度第 38 节。

4C3B3 接通可编辑俄语预览与显式确认发送；草稿修改后旧预览失效，已提交翻译可按原编号核对，人工改过的译文在当前页面返回编辑或明确拒绝后继续保留。长译文在窄屏输入框内滚动，确认按钮可达。浏览器验收使用隔离的模拟翻译与 Ozon 传输；服务端发送来源关联、完整草稿恢复及真实翻译质量仍待验证，见实施进度第 39 节。

4C3C1 增加首次有效译文的持久快照及原生回执关联，防止后续读取替换已确认依据。迁移 0018 必须先于新版 Worker 执行；冻结失败返回待核对，已发生的用量照常保留。发送命令与此证据的关联仍待下一步接线，见实施进度第 40 节。

4C3C2 接通翻译确认的服务端来源：原预览编号、不可变原译文及人工最终正文哈希进入发送回执和审计投影。重复提交不能更换来源，刷新核对保留原编号；确认不重新调用模型。普通原文发送保持兼容，本片不新增迁移。具体证据和未完成边界见实施进度第 41 节。

4C4 增加人工取消排队回复。取消与发送在同一会话控制对象中判定先后；已开始的请求和未知结果不能取消。最近发送提供明确确认、只读核对和原命令重试；迁移 0019 保留原有尝试与回执并恢复保护触发器。失败重试和平台结果核对仍待后续实现，见实施进度第 42 节。

4C5 为失败、已跳过和已取消的记录补充恢复草稿入口；已有草稿先确认替换，之后仍须预览并确认发送。旧译文候选失效，待核对翻译保留；结果待确认的发送不提供恢复快捷操作。详见实施进度第 43 节。

4D1 增加普通原文草稿的同标签页保存，按账号、成员、公司与会话隔离，刷新或断网重验后恢复。保存失败提示并保留当前输入；已接受发送先清理草稿，再解除原提交核对，避免旧正文复现为新草稿。仅覆盖原文，不包括跨设备或俄语编辑稿，详见实施进度第 44 节。

4D2 增加每会话持久导入顺序、固定导入上界的历史分页及独立追加读取 API；迟到与回填消息按导入序号补读，续页固定本批上界。游标绑定当前成员，每次读取复核授权；客户端校验边界、顺序与重复项。迁移 0020 保留原消息，服务端和客户端合同详见实施进度第 45 节；界面接线由下述 4D3 接续。

4D3 将追加读取接入消息中心，限制当前消息窗口与待显示批次，提供双向历史、较早更新定位、同标签页断线恢复和成员隔离的阅读位置。沿用官方 MessageScroller；普通草稿与发送确认不变。详见架构 11.3E 与实施进度第 46 节。

4D4 分别验证列表周期读取与焦点身份重验后的成员隔离，修正过窄的旧测试假设；消息处理栏压缩长姓名并提供完整姓名弹层，补充发送预览关闭时的焦点后备目标和唯一主内容地标。详见架构 11.3F 与实施进度第 47 节。

4D5 增加公司 IANA 时区设置、版本冲突与结果核对，统一现有工作区时间显示，并补齐其余会话处理弹窗在后台读取时的焦点返回。接口与界面边界见架构 11.3G，验证记录见实施进度第 48 节。

4D6 将消息附带的 SKU / 订单号接到已导入商品和 FBS 包裹，支持拆包分页、来源时间、冲突与缺失状态、读后撤权以及新消息到达时保留选中的订单。详见架构 11.3H 与实施进度第 49 节；真实平台归属语义仍需独立验证。

5A 接通回复策略的草稿、规则检查、发布、暂停与版本恢复，自动回复与主动通知分别配置。保存草稿不影响生效版本，发布原子冻结内容与检查时区；并发、回执丢失和撤权需核对或清理。这里只建立配置发布链路，尚未启用自动执行或 AI 回答测试。详见架构 11.3I 与实施进度第 50 节。

5B-1 增加知识草稿、不可变修订与分块、发布门禁、撤回、恢复和引用正文复核；真实本地 Workers/D1 验证事务。独立云端实验确认 Vectorize 可见性延迟及过滤、BGE-M3 的 1024 维响应，临时索引已删除。自动索引、导入页面、检索测试页面与模型回答接线仍待完成，详见架构 10.2A 与实施进度第 51 节。

## 2. 必须先理解的边界

1. Cloudflare 的部署按钮需要云账号、资源开通和必要的密钥；开源不代表云资源和模型调用免费。
2. Ozon 的订单、商品、买家聊天、商品问答、主动建聊是不同能力，必须按店铺权限及履约方式核实，不能互相推定。
3. 平台请求已发出但没有收到结果时，系统必须保留“结果待确认”；队列重试不能代替发送结果核对。
4. 人工接管能阻止尚未开始的 AI 发送；已经进入平台网络请求的消息不能承诺撤回。
5. Flue 的 AI 运行时数据与 DingBell 的业务消息、审计日志分别管理。原始推理轨迹不是消费者消息，也不是默认向客服展示的数据。
6. 本地构建与测试通过不等于云端或业务验收通过；跨阶段验收应分别记录已验证子场景与待复验范围。

## 3. 评审时需要确定的事项

| 编号 | 事项 | 本稿采用的建议 | 对施工的影响 |
| --- | --- | --- | --- |
| D-01 | AI 是否能执行退款、取消和发券 | 首版仅查询、回复、收集资料和转人工；资金与订单变更由人工在平台完成 | 改为自动执行需要增加审批、额度、补偿和平台操作审计 |
| D-02 | 试点规模和预算 | 暂用 10 公司、30 店铺、20 在线客服、每日 1 万条入站消息作为压测假设 | 不是销量预测、承诺容量或用户确认值 |
| D-03 | 试点店铺与 API 权限 | 阶段 1 获取官方文档与授权测试证据，形成能力矩阵 | 决定哪些售前入口、履约方式和主动通知可以上线 |
| D-04 | 开源许可证 | 建议 Apache-2.0；发布前由用户确认 | 当前不会添加许可证或对外发布 |
| D-05 | 商业计费 | 建议公司订阅加 AI 回复额度；支付服务暂以 Stripe 为候选 | 收费单位、价格、币种及经营主体确认后才能收真实费用 |
| D-06 | 数据保留与部署地域 | 本稿给出工程默认建议，试点前确认 | 影响存储成本、删除流程、恢复范围和模型供应商选择 |

评审通过可以接受本稿的建议值，也可以指定修改。任何未决项都保留明确的影响范围，不以沉默当作确认。
