# DingBell

AI customer support for ecommerce teams, built on Flue and Cloudflare.

The confirmed deployment targets are Cloudflare, Vercel and self-managed servers, sharing a business core with Pi Durable and platform adapters. This migration is planned; the current implementation remains Flue/Cloudflare. See [ADR-11](../../docs/04-research-and-decisions.md#adr-11-共用核心与三个完整部署目标2026-10-29) for the runtime choices, migration boundaries and acceptance criteria.

A separate Sandbox/Drives SQLite probe provides evidence for a business-storage candidate; full Vercel application integration remains unverified. See [deployment evidence and remaining checks](../../probes/deployment/README.md).

Persistent embedding admission limits installation-wide daily cost ceilings and query counts; generation keeps its independent company budget. Reloads read the original request, uncertain writes never retry automatically, and changed messages or evidence invalidate the result. Both pricing configurations, bindings and an enabled budget are required; defaults remain disabled. Company settings now provides manager-only test-budget creation, activation, pausing and usage estimates, backed by atomic audit records and replay-safe commands. New windows start paused and their caps stay immutable. Real answer-quality evaluation, background reconciliation and autonomous customer service remain pending. See architecture sections 7.7–7.9 and implementation progress sections 64–65. A 200-case synthetic quality corpus now exercises the real NVIDIA model through the existing Flue/SDK stack. Initial trials exposed citation-shape, decision and false-handoff claims. For local identity development, copy `.dev.vars.example` to `.dev.vars`, set a unique random `BETTER_AUTH_SECRET` of at least 32 characters (for example, generate one with `openssl rand -base64 32`), and set `APP_BASE_URL` to the exact origin used in the browser. Run `npm run db:migrate:local` before starting the application. Production origins require HTTPS; HTTP is allowed only for explicit loopback hosts. These files and secrets must stay untracked.

For a local UI demonstration without email delivery, stop the development server and run `npm run demo:local`. The command refuses any Wrangler database other than the checked-in `dingbell-local-only` placeholder, always invokes Wrangler with `--local`, and writes a random password to ignored `.dev.vars.demo-account.json` with owner-only permissions. Restart `npm run dev`, then sign in with the printed credentials. Re-running the command refreshes the same local account; deleting the credential file and re-running rotates its password. This is not a production bootstrap path or a public registration endpoint.

`GET /api/setup` reports whether identity and mail configuration are present. It does not test database availability, migrations or email deliverability. Public self-service registration and arbitrary company creation remain closed. There is no production seed endpoint or default account.

To create the first company, configure `RESEND_API_KEY`, a verified sender mailbox in `MAIL_FROM`, and a separate random `BOOTSTRAP_SECRET` of at least 32 characters. Open `/setup` and enter the installation secret in the form, never in the URL. Claim the installation with the company name and owner's name/email, set a password, and verify that email. Return to the same installation, authenticate with the verified owner's password, then select the created company. Refreshing the page requires re-entering the installation secret; progress is retained in D1. An interrupted claim does not expire into a fresh installation or promote an existing account. Once initialization finishes, the endpoint permanently closes and the deployment secret can be removed.

Owners and administrators can open `/workspace/team` to invite members or administrators, resend pending invitations, and revoke them. The recipient registers or signs in using the invited email, verifies it, and explicitly accepts the invitation. An old invitation cannot restore a removed membership. `/forgot-password` and `/resend-verification` acknowledge requests without revealing whether an email exists; `waitUntil` attempts delivery but is not a durable retry queue. Provider acceptance does not prove inbox delivery. Password reset invalidates earlier sessions.

The team page also supports role changes and member removal. Administrators can manage members and other administrators; only owners can grant or change ownership. Any change involving an owner requires the acting owner's current password. To hand over ownership, first grant another member the owner role, then change your own role; these are separate confirmed operations. A company must retain an owner. Removing a member does not delete the account, historical audits or memberships in other companies. New requests recheck membership, and the UI discards its old identity and company caches after a member change or an uncertain result.

Migrations contain application constraints beyond the generated Better Auth schema: unique company/user memberships, unique pending company/email invitations, three invitation-completion triggers in `0003_invitations.sql`, and two last-owner guards in `0004_membership_guards.sql`. Preserve these when regenerating the auth schema. Completed invitation flow records must survive member removal. Existing duplicate data makes migration fail rather than being silently deleted; inspect and reconcile it before deployment. The last-owner guards also reject deleting an owning user; account/company deletion is not exposed by the application.

Authentication and password confirmation use Better Auth. Member role updates and removals use a narrow conditional D1 write because the pinned SDK's member writes only filter by member ID. The final write also checks the company, displayed role, current actor membership, verified account and unexpired session. A stale target returns a conflict; owner guards run atomically in D1. Audits record the actor, company, target member and intended role change, without passwords. If the result audit fails after a write, the response is uncertain and clients must reread instead of replaying it.

Owners and administrators can manage multiple store connections at `/workspace/stores`. “添加店铺” first opens a platform chooser; Ozon is currently the only supported platform. Selecting it opens an in-page form for the store name, Client ID and API Key. Each Ozon seller account is saved as a separate store, so the chooser can be used repeatedly. Saving a store only encrypts and stores its credentials; Ozon API keys are never read from deployment files or returned to the browser. A separate read-only check samples credential access, product lists, chat lists and FBS order lists; each result is independent and expires after 24 hours. Replies and proactive chat creation remain unverified. These capability checks do not synchronize customer data or enable customer messaging. Pause preserves credentials; resume requires a new check; disconnect removes stored credentials while retaining the store and audit history. To reconnect a disconnected store, replace its credentials and check again.

Before saving credentials, set `STORE_CREDENTIAL_KEYS` in the ignored `.dev.vars` file to a JSON object such as `{"v1":"<base64-encoded 32 random bytes>"}` and set `STORE_CREDENTIAL_ACTIVE_KEY=v1`. Generate the key independently with `openssl rand -base64 32`; do not reuse the identity secret or a platform API key. On Cloudflare, store the key map as a Worker secret. Encryption uses native AES-256-GCM with a fresh nonce and company/store/account/revision context. Missing encryption configuration leaves account and existing metadata access usable while blocking credential writes and checks. API keys are never returned to the browser.

Owners and administrators have access to all stores in their company. Ordinary members only see explicitly granted stores; newly created stores grant them no access automatically. Grants reference the current membership, so removing a member deletes those grants and accepting a later invitation does not restore them. Migration `0005_stores.sql` enforces same-company store/member relationships. The credential envelope, current capability evidence and revision share one store row so conditional writes cannot leave a partially updated credential set. Audit events are separate and survive membership removal.

Platform credential replacement increments its version and invalidates old capability results. Encryption key versions are separate: retain old entries in `STORE_CREDENTIAL_KEYS` to decrypt existing records while new credential writes use the active key. This release has no bulk re-encryption command; do not remove an old key until every dependent record and retained backup has a tested recovery path. Back up encryption keys separately from D1. An uncertain write response must be checked by rereading the store, never by automatically resending the mutation.

After a fresh credential and chat-list check, a manager can separately enable buyer-chat synchronization. Each store has a `StoreCoordinator` Durable Object; alarms process one bounded provider page, while a minute Cron scans at most 50 due stores to repair missed wakeups. D1 separates each source’s enabled intent from the shared store lease, preserving checkpoints, messages and ingestion events. A page and its cursor commit atomically. Stopping, pausing, disconnecting or replacing credentials prevents old results from committing and preserves already imported history; resuming synchronization requires an explicit manager action. The continuing authorization belongs to the company and does not expire when the enabling manager signs out.
