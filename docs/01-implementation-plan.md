## 1. 项目目标与完成定义

DingBell 为中小电商公司提供 AI 与人工协作的客服系统。公司成员通过一个后台处理消费者的售前咨询、订单状态查询和售后问题。首个电商连接器面向 Ozon；主动通知是回复策略中的一种能力，按实际平台权限启用。

首版完成必须同时满足以下条件：

1. 自部署者能从公开仓库选择 Cloudflare、Vercel 或自建服务器部署完整应用，初始化后可使用自己的资源独立运行；各目标分别按 ADR-11 验收。
2. 公司可以注册、邀请成员、设置权限、连接店铺，并查看店铺实际可用的 API 能力。
3. 客户消息可以可靠接收；人工回复、AI 回复与主动通知经过同一发送管道，结果可追踪。
4. 人工接管、转交、已解决、重新打开等状态有确定含义，刷新或重新部署后不丢失。
5. 知识与回复策略支持草稿、测试、发布和版本追踪；回答能说明引用依据。
6. 会话日志可以按权限筛选、分析及导出 CSV，原始消息与译文保持区分。
7. 多租户隔离、重复事件、发送结果不明、任务恢复和升级恢复通过验收。
8. 商业托管使用相同核心代码；计费启用与否不改变核心客服功能是否能够自部署。

“页面可以打开”“演示数据能对话”“一条消息发送成功”分别只是局部验证，不能作为完整上线验收。

## 4. 施工顺序与里程碑

每阶段都应交付可运行增量、必要测试、迁移说明与验收证据。审计事件、公司范围校验、错误分类从首次实现对应功能时加入；第 7 阶段负责汇总查询与分析界面。

阶段退出条件中的验收编号按本阶段已实现功能及其依赖范围执行。一个 AC 跨越后续功能时，记录本阶段验证的子场景、证据和待复验部分；不能将局部通过标为整项通过。依赖齐备后复验完整适用范围，第 9 阶段统一放行。测试失败保持失败；只有经确认不在交付范围且已关闭的可选能力可以记为不适用，不能借此跳过必做能力。

用量记录、预算预留和日志/追踪内容脱敏从首次接入翻译、嵌入或模型调用时实现；阶段 8A 汇总基础用量和开源交付，阶段 8B 才加入可选商业订阅，不能先开放无计量或内容边界未受控的 AI 调用再补这些控制。

依赖主线：阶段 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8A → 9。阶段 8B 可选，不阻塞开源版发布，但阻塞商业版真实收费。

### 阶段 1：冻结范围并验证关键接入

**目的：** 在大规模编写业务代码之前，证实产品承诺所依赖的基础能力。

施工任务：

1.1 对照 Figma V4 与云端画板，列出页面、交互、状态和差异，冻结首版设计基线。

1.2 锁定 Flue 源码/发布版本、Node 开发环境、Vite、Wrangler、Better Auth、Drizzle 等依赖组合。按[逐篇文档核对](05-flue-documentation-audit.md)确认安装版本的文档与实际 API；初始化参考在临时目录生成后选择性合并，不覆盖现有文件。

1.3 制作最小 Cloudflare 验证应用，验证构建、DO 迁移、D1、R2、队列、Cron、域名路径和初始化。当前源码的构建入口为 flueWorkerConfig() customizer；应用绑定与迁移由项目维护，不按旧教程复制生成文件。

1.4 验证 Flue 的公开 dispatch/read/abort、观察和恢复接口与自有 ConversationController 的协作；验证原生 idempotencyKey 丢回执重放、载荷冲突、AI 运行中接管和敏感数据删除。客服控制状态放在自有 DO，不重复实现 Agent 调度；对照公开 extend 能力删减不必要的封装。禁止依赖 Flue 私有表或覆盖其 fetch/alarm 等保留生命周期。

1.4.1 验证运行时格式兼容性、已有数据升级与恢复；格式不兼容不得自动清空。当前源码仅对特定旧 schema 8 提供同构重标记，不据此承诺通用迁移。

1.5 用授权测试店铺形成 Ozon 能力矩阵：鉴权、聊天读取、回复、主动建聊、公开问答、商品、订单、物流、附件、回调、分页、限流及发送结果核对。

1.6 按 FBO、FBS、rFBS 或实际混合模式分别记录能力；核实套餐要求、消息窗口、状态字段和平台对通知内容的限制。

1.7 核对 Better Auth 在 Workers/D1 下的注册、组织邀请和迁移；核对模型调用与所选地域可用性。

1.8 按 ADR-08 优先验证 Cloudflare AI Search 是否能替代自建分块/嵌入管道；部署、权限、版本、引用、成本和恢复六项全部通过则采用，未通过则采用架构稿的 Vectorize 基线，只实现一套。

交付物：版本清单、设计差异单、Ozon 能力矩阵、Flue 兼容性记录、最小部署复现步骤、更新后的 ADR。

退出标准：AC-001、AC-011、AC-012、AC-016、AC-061、AC-085—AC-087、AC-093 对应验证有证据；每项平台承诺均为“可用”“明确不可用”或“暂不支持并已调整范围”。未知能力不得标为可用。关键路径失败时记录受影响模块及替代方案，其他独立模块可继续。

### 阶段 2：项目基础、账号与公司协作

2.1 建立一个 TypeScript 应用工程，前端 React/Vite，后端 Hono，沿用 Flue 的入口与构建方式。

2.2 加入格式检查、类型检查、构建、测试和迁移校验；开发、预览、生产资源分开。

2.3 集成 Better Auth、组织插件、邮件发送和公司初始化；定义角色及店铺范围权限。

2.4 建立首次部署认领机制，使用随机安装令牌创建初始所有者，完成后关闭安装入口；禁止公共部署“第一个访问者自动成为管理员”。

2.5 完成公司切换、成员邀请/撤销、角色调整、离职停用与最后一个所有者保护。

2.6 实现业务错误模型、请求追踪、只追加审计入口及统一公司范围访问方法。

交付物：可部署的登录与组织后台、迁移文件、权限矩阵、示例环境配置。

退出标准：AC-002—AC-010、AC-073 通过；两个公司的成员、列表、文件和操作互不泄漏；无模型密钥也能登录并看到待配置状态。

### 阶段 3：Ozon 连接器与可靠数据接收

3.1 将 Ozon 客户端、字段转换与能力判断集中在连接器中；外部 ID 按字符串处理。

3.2 实现凭证加密、验证、轮换、暂停和重连；能力结果展示检查时间和原因。

3.3 实现消息/商品/订单同步；使用持久游标、重叠窗口和唯一键去重。历史回填默认只导入，不触发 AI 或主动通知。

3.4 已核实可用的回调完成验证和事件落盘；其他入口使用官方允许的轮询方式。

3.5 为每店铺建立串行同步与限流控制；一次任务有页数、时间及重试上限，未完成部分使用游标续跑。

3.6 建立测试连接器、脱敏样本和错误注入：重复、乱序、限流、超时、凭证失效、游标过期。

交付物：Ozon 能力页面、同步任务、规范化实体、连接器合同测试与脱敏样本。

退出标准：AC-011—AC-022 通过；任务中断后可继续，重复输入不产生重复会话/消息；默认不开启自动对外回复。

### 阶段 4：人工消息中心与统一发送管道

4.1 实现三栏消息中心、分页搜索、负责人、等待状态、消费者与商品/订单上下文。

4.2 实现认领、接管、转交、内部备注、等待消费者、等待内部、已解决与重新打开。

4.3 建立发送意图、尝试、幂等键、会话版本和平台回执记录；仅统一发送管道持有外发能力。

4.4 中文输入生成可编辑俄语预览；确认后发送的内容必须与确认版本一致。修改草稿后旧预览失效。

4.5 实现已排队、发送中、已发送、失败、结果待确认、已取消、已跳过等展示和操作。

4.6 完成 1366×768 布局、上下文抽屉、固定输入区、独立滚动及重连恢复。

交付物：完整人工客服闭环、发送故障处理界面、对应 Figma 状态截图。

退出标准：AC-023—AC-030、AC-077—AC-080 通过；模拟平台下至少一次重复投递不会重复外发；真实平台的超时不被自动当成可重发失败。

### 阶段 5：知识库与策略发布基础

5.1 商品结构化事实、政策与使用说明分类型存储；知识源、修订版、分块和索引具备归属关系。检索实现按阶段 1 的 ADR-08 结果执行；托管索引承担通用处理时不重复自建。

5.2 实现草稿、索引中、可测试、已发布、撤回、失败重试；新版本未准备好时继续使用旧的有效版本。

5.3 建立公司/店铺/商品/语言/发布状态过滤，检索后再次检查有效性；订单事实通过订单工具读取。

5.4 为回复策略实现独立草稿和生效版本；同一策略组的启用范围与重叠规则确定优先级。

5.5 实现测试用例、知识缺口、人工修订与重新评估；测试结果不自动发布知识。

交付物：知识库、策略版本基础、检索测试数据和版本追溯界面。

退出标准：AC-040—AC-048 通过；跨公司知识命中数为 0；草稿及撤回内容不能进入新回复。

### 阶段 6：AI 自动回复与主动通知

6.1 使用 Flue 定义客服 Agent 与受控工具：知识检索、订单查询、资料收集、回复提交和转人工。提交前持久化稳定幂等键和冻结载荷，直接复用原生去重；首版不注册沙箱、任意代码执行和多 Agent 委派。

6.2 消费者文本与知识资料作为不可信内容；商家规则不授予工具执行权限，退款等未开放动作没有可调用工具。

6.3 AI 生成的内容先作为回复意图，绑定生成时不可变的 run_id、epoch、input_revision、policy_version；通过会话接待版本、当前权限、渠道能力、语言及策略检查后才可发送。当前上下文只用于校验，不能给旧输出重新附加新版本以恢复发送资格。

6.4 人工接管先提交控制状态，再中止 AI 执行；即使中止失败，旧版本生成的后续回复也不能通过发送检查。

6.5 主动通知使用“真实状态变更 → 规则匹配 → 延迟任务 → 发送前复核”；明确到期、静默时段、重复、取消及规则停用行为。

6.6 实现模型时间/轮次/预算上限、失败转人工、运营总开关和每店铺灰度开关。原生 durability.timeoutMs/maxAttempts 与模型轮次分别控制；验证异步中止和迟到完成，不能把超时视为外部请求已撤回。首轮不向繁忙的 Flue 会话追加新业务运行；多个 submission 共享 response 的版本归属与用量映射验证通过后，才启用繁忙合并。

6.7 建立售前、售中、售后、无依据、注入、权限、翻译和转人工评估集；按已记录标准评估，不凭主观演示放行。

## 6. 性能、容量与可用性目标

以下是首轮验收目标，不是目前已经测出的结果。测试使用付费 Workers、明确记录的区域、固定数据集和外部接口模拟器；真实模型和 Ozon 的耗时单独记录。

| 指标 | 暂定目标 | 测量方式 |
| --- | --- | --- |
| 基准负载 | 10 公司/30 店铺/20 在线客服；每日 10,000 条入站 | 固定生成种子，包含至少 100,000 条历史消息 |
| 入站峰值 | 10 条/秒连续 10 分钟；50 条/秒连续 60 秒 | 覆盖重复与乱序，允许队列缓冲，要求无数据丢失 |
| 普通 API 延迟 | P95 ≤ 800 ms | 不含文件传输、模型或平台等待；包含鉴权和数据库 |
| 接收持久化响应 | 模拟回调 P95 ≤ 1 秒 | 返回成功前已有可靠记录 |
| 工作台更新 | 已落业务库的新消息 P95 ≤ 8 秒可见 | 首版可见标签页增量轮询；不以平台事件发生时刻起算 |
| 新消息发现 | 不超过已配置轮询周期加处理积压 | 平台推送与轮询分别统计；周期以权限和限流实测确定 |
| AI 响应 | 记录 P50/P95；试点目标完成生成 P95 ≤ 30 秒 | 排除显式平台等待；超时转人工，不能静默卡住 |
| 发送正确性 | 确定性模拟场景重复外发为 0 | 外部结果未知必须保留待核对，不伪称全链路恰好一次 |
| 导出 | 100,000 行在 5 分钟内完成模拟数据导出 | 拆批生成，内存有界，超限不导致整个 Worker 崩溃 |
| 灾难恢复演练 | 暂定 RTO ≤ 4 小时，业务恢复点目标 ≤ 24 小时 | 按四类存储共同演练；外部已发消息必须对账后恢复发送 |
| 可用性 | 试点观察目标 99.5% | 应用入口、队列滞后、平台和模型分别计量，暂不作为对外 SLA |

D1 单库有容量与吞吐边界，不能把上述小规模基线外推为无限租户支持。达到存储或延迟预警阈值后，先分析索引、归档和热点，再评估拆库或 PostgreSQL；迁移作为独立变更评审。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

## 7. 成本与配额规划

每月成本模型：固定云费用 + Worker 执行 + D1 读写/存储 + DO 执行/存储 + 队列操作 + R2 文件/请求 + 向量/嵌入 + 邮件 + 模型 + 可选支付/监控。

模型成本按实际供应商账单口径计算：输入 tokens × 输入单价 + 输出 tokens × 输出单价 + 缓存/工具等供应商单独项目。翻译、总结、测试、失败重试也要计入内部技术用量；不能只数客户收到的回复。

阶段 1 输出可填写的成本表，分别代入低、基准、高三档流量。未知预算和供应商单价保留变量；不把估算当报价。每项费用记录计费单位、当前官方来源和计算日期。

建议配额分三层：部署总预算、公司预算、单次运行预算。80% 和 100% 阈值是待确认默认建议。超额先禁止新增 AI/自动通知并转人工，已发请求继续记录结果；人工工作台继续可用。

## 8. 质量和变更规则

1. 一个任务对应明确需求、代码、必要测试和验收证据；不以文件数或代码量衡量完成。
2. 权限、发送、接管、计量、版本发布、恢复属于关键逻辑，必须有异常和并发测试。
3. 文案或低风险样式调整通过针对性的视觉/交互检查，不为简单修改机械增加测试。
4. 应用配置、数据库迁移、队列事件和策略结构都需版本化；旧任务在升级后仍能识别。
5. 有破坏性的变更先备份、验证恢复与迁移，再评审执行；不能把代码回滚等同于数据回滚。
6. 优先使用公共 API 和维护可靠的依赖；不得为了省代码直接操作 Flue 私有存储结构。
7. 对范围变化记录影响：页面、表、接口、任务、预算、验收和交付阶段同时更新。
